┌──────────────────────────────────────────────────────────────────────────┐
│ BACKGROUND                                                               │
└──────────────────────────────────────────────────────────────────────────┘

Saat ini, sistem sales memproses order dengan logika yang tersebar di berbagai 
layer aplikasi, menyulitkan maintenance dan testing. Tidak ada pemisahan jelas 
antara business logic, application orchestration, dan technical concerns.

Tantangan:
  • Business rules tercampur dengan database logic
  • Query dan command tidak terpisah (N+1 queries, over-fetching data)
  • Sulit untuk melakukan perubahan pada business logic tanpa meng-affect 
    infrastructure layer
  • Event handling untuk domain process belum ada (audit trail, notifications)

Visi: Menerapkan DDD + Hexagonal + CQRS untuk memisahkan concerns dan membuat 
sales domain lebih maintainable, testable, dan scalable.

┌──────────────────────────────────────────────────────────────────────────┐
│ OBJECTIVE                                                                │
└──────────────────────────────────────────────────────────────────────────┘

Membangun Sales Order Processing System yang:
  ✓ Menggunakan DDD untuk model domain yang rich dan self-validating
  ✓ Menggunakan Hexagonal Architecture untuk isolation dari infrastructure
  ✓ Menggunakan CQRS untuk optimalisasi query dan event handling
  ✓ Mengimplementasikan business logic sederhana: order creation → confirmation 
    → completion dengan automatic commission calculation
  ✓ Mendukung domain events untuk audit trail dan side effects

Tujuan Pembelajaran:
  • Memahami bagaimana DDD entities & value objects melindungi business rules
  • Melihat bagaimana Hexagonal ports mengisolasi domain dari external systems
  • Melihat bagaimana CQRS memisahkan write model (commands) dari read model 
    (queries)
  • Praktik event sourcing untuk state changes

│ FR-001: DDD Domain Model - Sale Order Aggregate                         │

│ Judul: Membuat Sale Aggregate dengan value objects dan business rules   │
│                                                                         │
│ Kondisi Awal:                                                          │
│   • Tidak ada domain model untuk order processing                       │

│ Tindakan:                                                               │
│   1. Identifikasi Sale Aggregate root dengan:                           │

│                                                                         │

│   ✓ Business rules terlindungi dari external access                     │
│   ✓ Type-safe value objects mencegah invalid state                      │
│   ✓ Domain model dapat di-test tanpa infrastructure                     │
│                                                                         │
│ Business Logic Examples:                                                │
│   - Validasi: Quantity > 0, Price > 0, Customer harus exist             │

┌─────────────────────────────────────────────────────────────────────────┐
│ FR-002: Hexagonal Architecture - Port & Adapter Pattern                 │
├─────────────────────────────────────────────────────────────────────────┤
│ Judul: Mengisolasi domain dari infrastructure melalui ports             │
│                                                                         │
│ Kondisi Awal:                                                          │
│   • Domain logic tergantung pada database queries (Eloquent)            │
│   • Payment processing hardcoded ke 1 provider                          │
│   • Sulit untuk test tanpa database dan external services               │
│                                                                         │
│ Tindakan:                                                               │
│   1. Definisikan Primary Ports (outbound dari domain):                  │
│      - SaleRepositoryInterface                                          │
│        └─ save(Sale): void                                              │
│        └─ getById(SaleId): Sale                                         │
│      - PaymentGatewayInterface                                          │
│        └─ process(payment): PaymentResult                               │
│      - CommissionServiceInterface                                       │
│        └─ calculate(sale): Commission                                   │
│   2. Implementasi Adapters (framework-specific):                        │
│      - EloquentSaleRepository implements SaleRepositoryInterface        │
│      - LaravelPaymentGatewayAdapter implements PaymentGatewayInterface  │
│      - DatabaseCommissionService implements CommissionServiceInterface  │
│   3. Konfigurasi Dependency Injection di container:                     │
│      - Bind interfaces ke konkret implementations                       │
│      - Mudah swap implementation (e.g., test mock vs production)         │
│   4. Secondary Port (inbound):                                          │
│      - REST API Controller sebagai adapter untuk HTTP                   │
│      - Command handlers sebagai aplikasi entry points                   │
│                                                                         │
│ Hasil:                                                                   │
│   ✓ Domain tidak bergantung pada framework (Laravel, Eloquent)          │
│   ✓ Infrastructure dapat ditest secara independen                       │
│   ✓ Mudah mengganti payment provider, database, atau API               │
│   ✓ Domain code 100% testable dengan mock repositories                  │
│                                                                         │
│ Architectural Benefit:                                                  │
│   - Left side (Domain): Use cases & entities (framework-agnostic)        │
│   - Right side (Infrastructure): Repositories & gateways (implementation)
│   - Top side (API): REST Controllers & CLI commands (request adapters)   │
│   - Bottom side (Database): Persistence layer (response adapters)        │
│                                                                         │
│ Priority: MUST                                                          │
│ Traces to: Hexagonal Learning Goal #1                                   │

┌─────────────────────────────────────────────────────────────────────────┐
│ FR-003: CQRS - Separate Commands from Queries                           │
├─────────────────────────────────────────────────────────────────────────┤
│ Judul: Memisahkan command model (write) dari query model (read)         │
│                                                                         │
│ Kondisi Awal:                                                          │
│   • Satu model untuk read dan write (tidak optimal)                     │
│   • Complex queries dengan multiple joins dan N+1 problems              │
│   • Aggregated data harus di-compute on-the-fly                         │
│   • Real-time reports sulit dan lambat                                  │
│                                                                         │
│ Tindakan:                                                               │
│   1. Tentukan Command Side (Write Model):                               │
│      Commands (input/intent):                                           │
│        - CreateSaleCommand(customerId, items)                           │
│        - ConfirmSaleCommand(saleId)                                     │
│        - CompleteSaleCommand(saleId)                                    │
│        - CancelSaleCommand(saleId, reason)                              │
│      Handlers (orchestration):                                          │
│        - CreateSaleHandler → validasi + create aggregate + save         │
│        - ConfirmSaleHandler → retrieve + confirm + save + emit events   │
│      Output: Domain events (SaleCreatedEvent, SaleConfirmedEvent, etc.)  │
│                                                                         │
│   2. Tentukan Query Side (Read Model):                                  │
│      Queries (projection/read):                                         │
│        - GetSaleByIdQuery(saleId) → detail order                        │
│        - ListSalesQuery(customerId, status, page) → paginated orders    │
│        - GetSalesReportQuery(period) → aggregated metrics               │
│        - GetCommissionSummaryQuery(period) → commission report          │
│      Handlers:                                                          │
│        - Optimized for read performance (flat tables, denormalized)      │
│        - Index on frequently queried fields                             │
│      Data source: Read models atau materialized views                   │
│                                                                         │
│   3. Implementasi Event Projections:                                    │
│      Ketika SaleConfirmedEvent emitted:                                 │
│        → Update SalesListReadModel (aggregate cache)                    │
│        → Update CustomerSalesCountReadModel                             │
│        → Trigger CommissionCalculationProjection                        │
│   4. Eventual Consistency:                                              │
│      - Write happens immediately (command)                              │
│      - Read model updates via event handlers (async/eventual)           │
│      - Client might see stale data briefly (acceptable for reporting)    │
│                                                                         │
│ Hasil:                                                                   │
│   ✓ Command handlers fokus pada business logic & state changes          │
│   ✓ Query handlers optimized untuk performance (no joins needed)         │
│   ✓ Read models pre-computed, fast to serve to UI                       │
│   ✓ Easy to scale read side independently                               │
│   ✓ Audit trail via domain events                                       │
│                                                                         │
│ Business Logic in CQRS Context:                                         │
│   - Commission Calculation:                                             │
│     Event: SaleCompletedEvent                                           │
│     Projection: IF sale.total > 1M THEN commission = 5% ELSE 3%         │
│                 Store in CommissionReadModel for reporting               │
│   - Sales Metrics:                                                      │
│     Event: SaleConfirmedEvent                                           │
│     Projection: Increment daily_sales_count, update revenue_total        │
│                                                                         │
│ Priority: MUST                                                          │
│ Traces to: CQRS Learning Goal #1                                        │
└─────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────┐
│ FR-004: Domain Events & Event Handlers                                  │
├─────────────────────────────────────────────────────────────────────────┤
│ Judul: Menggunakan domain events untuk menangani side effects            │
│                                                                         │
│ Kondisi Awal:                                                          │
│   • Side effects (emails, notifications, logs) ada di command handler    │
│   • Tanpa event sourcing, sulit track perubahan state                    │
│   • Multiple systems tidak tahu tentang perubahan domain                 │
│                                                                         │
│ Tindakan:                                                               │
│   1. Definisikan domain events dalam domain layer:                      │
│      - SaleCreatedEvent(saleId, customerId, total, timestamp)           │
│      - SaleConfirmedEvent(saleId, confirmedAt)                          │
│      - SaleCompletedEvent(saleId, completedAt, commission)              │
│      - SaleCancelledEvent(saleId, reason, cancelledAt)                  │
│   2. Publikasikan events dari aggregate methods:                        │
│      Sale.confirmSale() {                                               │
│        this.status = OrderStatus::CONFIRMED                             │
│        this.confirmedAt = now()                                         │
│        this.recordEvent(new SaleConfirmedEvent($this->id))  ← publish   │
│      }                                                                   │
│   3. Register event subscribers/handlers:                               │
│      - SendConfirmationEmailHandler → ketika SaleConfirmedEvent         │
│      - UpdateSalesMetricsHandler → ketika SaleCompletedEvent            │
│      - CalculateCommissionHandler → ketika SaleCompletedEvent           │
│      - LogAuditTrailHandler → untuk semua events                        │
│   4. Implement event bus untuk dispatch:                                │
│      - Sync atau async dispatch (dapat di-configure)                    │
│      - Retry mechanism untuk failed handlers                            │
│                                                                         │
│ Hasil:                                                                   │
│   ✓ Clear audit trail dari semua state changes                          │
│   ✓ Side effects decoupled dari command handlers                        │
│   ✓ Mudah add new behaviors (e.g., new event handler) tanpa modify code │
│   ✓ Event-driven architecture enables async processing                  │
│                                                                         │
│ Priority: SHOULD                                                        │
│ Traces to: CQRS & DDD Learning Goal #2                                  │

Contoh business logic sederhana yang diimplementasikan dalam sales domain:

1. **ORDER CREATION & VALIDATION**
   ─────────────────────────────────
   When: CreateSaleCommand(customerId, items[])
   
   Rules:
   • Customer harus exist (query customer via CustomerId)
   • Setiap item quantity > 0
   • Setiap item price > 0
   • Total = SUM(item.price × quantity) harus ≥ Rp 50.000 (minimum order)
   • Maksimal 20 line items per order
   
   Result:
   • Sale aggregate created dengan status PENDING
   • SaleCreatedEvent recorded
   • No payment taken yet (just record intent)

2. **ORDER CONFIRMATION & PAYMENT**
   ────────────────────────────────
   When: ConfirmSaleCommand(saleId)
   
   Rules (per business policy):
   • Status harus PENDING (tidak boleh double-confirm)
   • Stock check: semua items tersedia di inventory (hypothetical)
   • Lock harga: simpan actual price di sale (price tidak boleh berubah)
   • Process payment via PaymentGatewayInterface
     └─ IF payment success → status = CONFIRMED
     └─ IF payment fails → throw PaymentFailedException, stay PENDING
   
   Result:
   • Sale status berubah PENDING → CONFIRMED
   • Payment captured
   • SaleConfirmedEvent recorded dengan payment_id
   • Customer email dikirim: "Pesanan Anda telah dikonfirmasi"

3. **ORDER COMPLETION & COMMISSION**
   ─────────────────────────────────
   When: CompleteSaleCommand(saleId) — typically triggered after delivery
   
   Rules:
   • Status harus CONFIRMED (only complete confirmed orders)
   • Calculate commission based on:
     └─ IF total amount > Rp 1.000.000 → 5% commission
     └─ ELSE IF total amount > Rp 500.000 → 3% commission
     └─ ELSE → 1% commission
   
   Commission calculation example:
   • Sale amount: Rp 750.000
   • Commission rate: 3%
   • Commission amount: Rp 22.500
   
   Result:
   • Sale status berubah CONFIRMED → COMPLETED
   • Commission amount calculated dan stored
   • SaleCompletedEvent recorded dengan commission
   • Metrics updated: daily_sales_total, daily_sales_count, agent_commission
   • Notification sent to agent: "Anda mendapatkan komisi Rp 22.500 untuk order #123"

4. **ORDER CANCELLATION**
   ─────────────────────
   When: CancelSaleCommand(saleId, reason)
   
   Rules:
   • Hanya bisa cancel dari status PENDING atau CONFIRMED
   • Jika CONFIRMED: refund payment (via PaymentGateway.refund())
   • Jika PENDING: nothing to refund
   • Store cancellation reason untuk audit
   
   Result:
   • Sale status → CANCELLED
   • SaleCancelledEvent recorded dengan reason
   • Payment refunded if applicable
   • Customer notified

5. **COMMISSION DISTRIBUTION**
   ──────────────────────────
   When: CommissionCalculatedEvent fired (after SaleCompletedEvent)
   
   Rules (hypothetical agent system):
   • Commission belongs to agent who created the order
   • Commission is "earned" on completion (not on confirmation)
   • Commission can be withdrawn monthly
   • Track commission per agent in CommissionReportRM
   
   Result:
   • Agent.totalCommission += calculated commission
   • CommissionReportRM updated
   • Agent can see in dashboard: "Total komisi bulan ini: Rp 500.000"

┌──────────────────────────────────────────────────────────────────────────┐
│ KEY LEARNINGS                                                            │
└──────────────────────────────────────────────────────────────────────────┘

✓ DDD - Domain Entities & Value Objects encapsulate business rules
  └─ Impossible to create invalid Sales (validation in constructor)
  └─ Type-safe with value objects (Money, SaleId) vs primitive types

✓ Hexagonal - Ports & Adapters isolate domain from infrastructure
  └─ Domain doesn't know about Laravel, Eloquent, or HTTP
  └─ Can test domain with mock repositories without database

✓ CQRS - Separate commands (write) from queries (read)
  └─ Commands orchestrate state changes, don't return data
  └─ Queries read from optimized read models (fast, no joins)
  └─ Projections keep read models synchronized with write model

✓ Events - Audit trail & decoupled side effects
  └─ Every state change is recorded as a domain event
  └─ Event handlers manage side effects (email, notifications, metrics)
  └─ Easy to extend with new behaviors (add new event subscriber)

✓ Ubiquitous Language - Business terms in code
  └─ "Sale", "LineItem", "OrderStatus", "confirm", "complete"
  └─ Developers and stakeholders speak the same language
